# ADR 0008 — CLI framework and interface

- **Status:** Accepted
- **Date:** 2026-09-25

## Context

ExcelPilot's primary interface is the command line. It must be scriptable, produce
machine-readable output for automation, render human-readable summaries for an
operator, and never expose an unsafe option without a policy control.

The sibling project `AirtelGLAutomation` uses a PySide6 GUI with a thin
`app.main:main` entry point. The specification asks for a dashboard but explicitly
warns against an unnecessarily complex frontend.

## Decision

**Typer** for the CLI, matching the one required-dependency policy (ADR-0002).

### Command surface

```
excelpilot inspect WORKBOOK [--json]
excelpilot plan    WORKBOOK --task TEXT [--json]
excelpilot run     WORKBOOK --task TEXT [--dry-run] [--output PATH]
                           [--config PATH] [--allow-paid-calls] [--no-ai]
                           [--run-id ID] [--verbose] [--json]
excelpilot diff    A.xlsx B.xlsx [--json]
excelpilot verify  WORKBOOK --run RUN_ID [--json]
excelpilot replay  RUN_ID [--json]
excelpilot runs    [--limit N]
excelpilot policy  explain --json      # show the effective rule set and thresholds
```

`run` is the only command that mutates anything, and it defaults to refusing to
overwrite the source.

### Output contract

Every command supports `--json` and emits a **stable, versioned** JSON document on
stdout. Human-readable output goes to stdout; diagnostics go to stderr. This makes
`excelpilot run … --json | jq` reliable, which is the actual integration need.

### Unsafe options are policy-controlled, not hidden

- `--allow-paid-calls` gates every live JEV/LLM call. Without it the code path
  raises `PaidCallBlocked` — a control, not a warning.
- `--output` is resolved through the path sandbox; a path escaping the workspace is
  rejected regardless of flags.
- There is no `--force`, `--no-verify`, or `--skip-policy`. A caller cannot request
  that verification be skipped, because the alternative is a flag that disables the
  property the product exists to provide.

### Exit codes

| Code | Meaning |
|---|---|
| 0 | Success, and verification passed |
| 1 | Unexpected internal error |
| 2 | Usage error (bad arguments) |
| 3 | Policy denied the run |
| 4 | Approval required and not granted |
| 5 | Verification failed — the run failed even though a file was written |
| 6 | Paid call blocked (`--allow-paid-calls` absent) |

Code 5 is load-bearing: it makes "saved successfully but not verified" a distinct,
non-zero outcome rather than a success.

### Dashboard deferred to last

Built only after the CLI and core are verified, per the agreed sequencing. It consumes
the same backend services as the CLI and **cannot bypass policy**: the dashboard calls
`app.RunOrchestrator`, the same entry point the CLI uses. There is no
dashboard-specific execution path.

## Alternatives considered

| Option | Why rejected |
|---|---|
| `argparse` | No subcommand help, no type coercion, no completion; every command needs boilerplate |
| `click` directly | Typer is a thin typed layer over it; same dependency, less code |
| `rich-click` | Adds a dependency for marginal formatting gain |
| A web UI as the primary interface | Rejected: harder to script, harder to test, and a poor fit for an operations tool driven by operators and CI |
| Full dashboard now | Deferred deliberately — a UI built before the engine is verified tends to freeze the engine's shape |
